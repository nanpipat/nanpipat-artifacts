# Kubernetes & Rancher — ถ้ากล่องตายตอนตีสาม ใครไปตื่นมา restart มัน

## จากคนคุมกล่องทีละใบ สู่ผู้จัดการคลังสินค้า

[ตอนที่แล้ว](/courses/docker-fundamentals) เราคุมกล่อง container ทีละใบได้แล้ว — `ps`, `logs`, `restart` ครบมือ

แต่คำถามที่ควรถามต่อคือ: **ถ้าเราดูแลระบบที่มีกล่องเป็นร้อยใบ ลูกค้าหลายสิบราย แล้วกล่องตายตอนตีสาม — ใครไปตื่นมา restart มัน**

Docker เป็นคนคุมกล่องทีละใบที่เก่งมาก แต่เขาไม่ได้ทำงานเหล่านี้ให้:

- กล่องตายแล้วใครเปิดใหม่ (และเปิดกี่ครั้งได้กี่ครั้ง)
- คนเข้าเว็บเยอะแล้วใครเพิ่มกล่อง
- กล่องอยู่คนละเครื่อง ใครจัดการว่างานไปตกที่ไหน
- เปลี่ยนเวอร์ชันใหม่แบบไม่ดับ ทำยังไงให้ไม่มีช่วงหยุด

**Kubernetes (K8s) คือผู้จัดการคลังสินค้า** — เขาดูแลกล่องทั้งคลังให้เอง ตลอด 24 ชั่วโมง

เกร็ดชื่อ: K8s = **K** + 8 ตัวอักษร (ubernete**s**... นับตัวอักษรระหว่าง K กับ s) + **s** ชื่อย่อแบบคนในวงการ

และสิ่งที่ K8s **ไม่ใช่** ก็สำคัญเท่ากัน — เขาไม่ได้ซ่อมแอปที่เขียนพังให้ ไม่ได้ทำให้โค้ดแย่กลายเป็นโค้ดดี เขาแค่ดูแลกล่องให้เป็นตามที่เราสั่ง

ส่วน **Rancher** ที่อยู่ในชื่อคอร์ส — เขาไม่ใช่คู่แข่งของ K8s แต่เป็น **หน้าจอที่ครอบ K8s อีกที** ทำให้เรามองเห็นและกดอะไรต่างๆ ได้โดยไม่ต้องพิมพ์คำสั่ง คนสับสนเรื่องนี้บ่อยมาก

## ร้านกาแฟ ☕: ภาพเดียวที่อธิบาย K8s ได้ทั้งระบบ

ถ้าอ่านถึงตรงไหนเริ่มงง ให้ย้อนกลับมาที่ร้านกาแฟหลังนี้เสมอ

- **Pod** = พนักงานชงกาแฟหนึ่งคน
- **Deployment** = ผู้จัดการฝ่ายบุคคล — ตั้งไว้ว่าต้องมีคนชง 3 คน ใครลาออกก็จ้างคนใหม่ให้ทันที
- **Service** = เคาน์เตอร์รับออเดอร์ — ลูกค้าสั่งที่เคาน์เตอร์ ไม่ได้เข้าไปจับคนชงเป็นรายคน
- **Namespace** = สาขาของร้าน — อยู่คนละสาขาก็เลยหากันไม่เจอ

ประโยคที่อยากให้ติดหูที่สุดของทั้งคอร์ส:

> **ลูกค้าไม่เคยรู้ว่าวันนี้ใครเป็นคนชง และไม่จำเป็นต้องรู้ด้วย**

นี่คือเหตุผลว่าทำไม pod ตายแล้วระบบยังใช้ได้ — Deployment จ้างคนใหม่มาแทนก่อนที่ลูกค้าจะรู้ตัว

### Pod เป็นของชั่วคราว — ชื่อสุ่มคือเรื่องปกติ

ชื่อ pod ลงท้ายด้วยอักษรสุ่มๆ อย่า `menu-api-7d9f4b-x2vkl` เพราะมันเกิดใหม่ได้ตลอด เคสจริงที่เจอบ่อย: ลูกค้า/dev ส่งชื่อ pod มาให้ดู พอไปหาแล้วไม่เจอ เพราะตัวเก่าตายไปแล้วเกิดตัวใหม่ — **ให้หาจากชื่อ workload (Deployment) แทน ไม่ใช่ชื่อ pod ตรงๆ**

และเพราะ pod เป็นของชั่วคราว ถ้าจะ restart งาน ให้ทำที่ระดับ workload เสมอ ไม่ใช่ไล่ลบ pod ทีละตัว

## Desired State: เราไม่สั่งขั้นตอน เราบอกผลลัพธ์ที่อยากได้

นี่คือแนวคิดที่สำคัญที่สุดของวัน เข้าใจตรงนี้ = เข้าใจ K8s ไปครึ่งทาง

ลองนึกถึงการตั้งแอร์ 25 องศา — เราไม่ได้สั่งว่า "เป่าแรง 3 นาที แล้วหยุด แล้วเป่าอีก" เราแค่บอก **ผลลัพธ์ที่อยากได้** แล้วแอร์จัดการเอง

K8s ก็แบบนั้น — เราเขียนไว้ว่า "ต้องมี `menu-api` 3 ตัว" จากนั้นไม่ว่าจะเกิงอะไรขึ้น ระบบจะพยายามดันให้เป็น 3 ตัวเสมอ

ผลที่ตามมาและทำให้หลายคนตกใจ: **ลบ pod ไปแล้วมันเกิดใหม่ = เรื่องปกติ ไม่ใช่ผี** — เพราะ K8s กำลังทำงานตามที่สั่งไว้เป๊ะๆ

คำถามทวน: ถ้าอยากให้ pod หายจริงๆ ต้องทำที่ไหน — ตอบว่า **ที่ Deployment ไม่ใช่ที่ pod** (เพราะลบปลายหาง หัวใจยังสั่งให้เกิดใหม่อยู่)

## เส้นทางของ request: อ่าน error code เป็นก็รู้ว่าไปดูตรงไหน

ตอนลูกค้าเข้าเว็บ คำขอเดินทางแบบนี้:

```text
ลูกค้า → Ingress (ประตูร้าน) → Service (เคาน์เตอร์) → Pod (คนชง)
```

และ error code ที่ลูกค้าเห็น บอกตำแหน่งที่พังได้แม่นมาก:

| ลูกค้าเห็น | พังตรงไหน | ไปดูต่อที่ |
|---|---|---|
| **404** | ประตู (route ผิด) | Ingress |
| **502 / 503** | เคาน์เตอร์ (หาคนชงไม่ได้) | Service / Pod |
| **500 / timeout** | ตัวแอปเอง | Logs ของ Pod |

กฎจำง่ายๆ: **pod ปกติดี แต่ลูกค้าเข้าไม่ได้ → มองที่ Service/Ingress ก่อน ไม่ใช่เข้าไปแก้ pod**

## อ่านสถานะ Pod ให้เป็น: กับดัก Running 0/1

หน้าจอ Workloads จะเห็นตัวเลขแบบ `3/3` หรือ `0/1` — ตัวเลขขวาคือจำนวนที่ต้องมี ตัวเลขซ้ายคือจำนวนที่พร้อมใช้จริง

**กับดักอันดับหนึ่งของคอร์สนี้: `Running 0/1`**

มันหลอนตรงที่คำว่า Running ทำให้เราตอบลูกค้าไปว่า "ระบบปกติครับ" ทั้งที่แอปยังไม่พร้อมทำงานเลย — **ให้ดูตัวเลข READY ทุกครั้ง ไม่ใช่ดูแค่คำว่า Running** และคอลัมน์ RESTARTS ที่เพิ่มขึ้นเรื่อยๆ ก็คือสัญญาณว่ามีปัญหา แม้สถานะจะเป็น Running

### การ์ดอาการ 6 แบบที่ต้องเจอ

อ่านเป็นภาษาคนก่อน แล้วค่อยจับคู่ชื่อเทคนิค:

- **"ยังไม่มีที่ให้ยืนทำงาน"** = `Pending` — ขอทรัพยากรไม่ได้ (หลาย pod Pending พร้อมกัน = ปัญหาระดับ cluster → escalate ทันที อย่าไล่ทีละตัว)
- **"เข้างานแล้วเป็นลมทุกรอบ พักยาวขึ้นเรื่อยๆ"** = `CrashLoopBackOff` — แอปพังซ้ำๆ K8s จึงเว้นระยะลองใหม่นานขึ้นเรื่อยๆ (เจอบ่อยที่สุด)
- **"ยังไม่ได้เข้างานเลย เรียกไม่ตอบ"** = `ImagePullBackOff` — ดึง image ไม่ได้ (tag ผิด / ไม่มีสิทธิ์ registry / เน็ตไปไม่ถึง)
- **กำลังจ้างคนใหม่** = ContainerCreating — รอแป๊บนึงได้ นานเกินไปค่อยดู Events

CrashLoopBackOff จำแค่ 3 คำต้นเหตุหลัก: **connection / config / permission** — และอย่าเสียเวลา restart ซ้ำหลายรอบ ถ้าสาเหตุยังอยู่มันพังอีกแน่นอน

### กฎทองของทั้งคอร์ส: Events vs Logs

ประโยคเดียวที่อยากให้ท่องพร้อมกันสักครั้ง:

> **pod ยังไม่เริ่มรัน → ดู Events · pod เคยรันแล้วพัง → ดู Logs**

เพราะอะไร — ถ้า image ยังดึงไม่ได้ แอปยังไม่ได้ทำงานเลย มันจึง **ไม่มี log ให้ดู** เปิด log มาเจอทะเลขาว แต่ Events จะบอกว่า K8s พยายามทำอะไรแล้วติดตรงไหน

วิธีจำ: **Log = เสียงจากตัวแอป / Events = เสียงจาก K8s เอง**

## Rancher: หน้าจอที่ทำแทนคำสั่งได้เกือบหมด (แต่ไม่มี undo)

Rancher ทำแทน kubectl ได้เกือบทุกอย่าง ดู workload ดู log ดู events ครบ ไม่ต้องกลัวว่าต้องท่องคำสั่ง

แต่มีข้อควรระวังที่ต้องรู้ตั้งแต่วินาทีแรก: **ไม่มีปุ่ม undo — ทุกปุ่มมีผลจริงกับ production ทันที**

### 3 อย่างที่ต้องเลือกให้ถูก ก่อนกดอะไรก็ตาม

**Cluster → Namespace → Workload** — อ่านชื่อ cluster ออกเสียงในใจทุกครั้งก่อนกดปุ่มอะไร

เคสอุบัติเหตุคลาสสิก: ตั้งใจ restart ตัวใน staging แต่เผลออยู่ prod — เพราะหน้าจอหน้าตาเหมือนกันทุก cluster

และประเด็นเรื่อง "หาไม่เจอ": **Namespace ผิดคือสาเหตุอันดับหนึ่ง** — อยู่ default ทั้งที่งานอยู่อีก namespace ก็มองไม่เห็นอะไรเลย

### 4 ที่ที่ต้องเปิดทุกครั้งที่เจอเคส

1. **Workloads** — ดูตัวเลข READY (ไม่ใช่แค่คำว่า Running)
2. **Log** — และอย่าลืมปุ่ม **Previous** ⭐ — ดู log ของ "รอบที่พัง" ไม่ใช่รอบที่เพิ่งเกิดใหม่ (ตัวใหม่ยังไม่ทันพัง ข้อมูลจึงยังสะอาด) เปิด Timestamps ด้วยเพื่อเทียบเวลากับที่ลูกค้าแจ้ง
3. **Events** — ตอนที่ log ไม่มีอะไรเลย
4. **RESTARTS + หน้าจอของตัวที่ดูสงบ** — ตัวที่เงียบสนิทอาจมีประเด็นซ่อนอยู่

### Redeploy vs ลบ pod

**Redeploy ปลอดภัยกว่าที่คิด** — เพราะมันเปลี่ยนทีละตัว (rolling update) ระบบไม่ดับระหว่างทาง ต่างจากการไล่ลบ pod ทีละตัวเอง แต่กฎเดิมยังอยู่: **เก็บ log ก่อน redeploy เสมอ** ส่วน Rollback มีให้ใช้ แต่ต้องขออนุมัติก่อน ไม่ใช่ตัดสินใจเอง

## kubectl: ก๊อปแนบ ticket ชัดกว่า screenshot

ทำไมต้องรู้ทั้งที่มี Rancher อยู่แล้ว — เหตุผลที่ตรงใจทีม support ที่สุด: **output แบบ text ก๊อปแนบ ticket ได้เลย ชัดกว่า screenshot ละเอียดครึ่งหน้าจอ**

ใช้ผ่าน kubectl Shell ใน Rancher ได้เลย ไม่ต้องลงอะไรเพิ่ม ชุดที่คุ้มที่สุด:

```bash
kubectl get pods -n <namespace>          # -n สำคัญมาก ลืมแล้วไม่เห็นอะไรเลย
kubectl get pods -A | grep -v Running    # กวาดหาตัวมีปัญหาทั้ง cluster ไวมาก
kubectl describe pod <ชื่อ> -n <ns>       # เลื่อนลงไปอ่านท้ายสุด — ส่วน Events
kubectl logs <ชื่อ> -n <ns> --previous   # log ของรอบที่พัง (ครั้งที่ 3 ที่ย้ำ — ตั้งใจ)
kubectl get events -n <ns> --sort-by=.lastTimestamp   # ไทม์ไลน์ทั้ง namespace
kubectl port-forward svc/<ชื่อ> 8080:80  # แยกว่าปัญหาอยู่ที่แอปหรือที่ ingress
```

`port-forward` คือคู่หูของ `curl localhost` จากตอนก่อน — เข้าถึงตัวแอปตรงๆ ข้ามประตูทั้งหมด ถ้าตรงนี้ใช้ได้แต่เว็บจริงเข้าไม่ได้ ปัญหาก็อยู่ที่ทางเข้า ไม่ใช่ตัวแอป

## ทำได้เอง vs ส่งต่อ: อ่านได้เสมอ เขียนต้องมีคนอนุมัติ

เส้นแบ่งที่ชัดที่สุดของงาน support บน K8s:

**ทำได้เอง (อ่านอย่างเดียว — ไม่เปลี่ยนอะไรในระบบ):**
- ดู workload, log, events, describe, port-forward เพื่อพิสูจน์สมมติฐาน
- เก็บหลักฐานให้ครบก่อนแจ้งทีมอื่น

**ต้องส่งต่อ (เขียน/เปลี่ยนระบบ — ต้องมีคนอนุมัติ):**
- แก้ secret / config ที่ผิด, เปลี่ยน image tag, rollback, scale ที่กระทบ production

และเมื่อส่งต่อ ให้ส่งแบบที่ dev แก้ได้เร็วที่สุด: **ชื่อ workload + namespace + cluster + log ช่วงเวลาที่ลูกค้าแจ้ง + Events ของช่วงนั้น + สิ่งที่เปลี่ยนไปก่อนหน้า** — dev ที่ได้ข้อมูลชุดนี้มักหาสาเหตุเจอภายในไม่กี่นาที

ข้อห้ามสุดท้ายเรื่อง **Secret**: ค่าที่เห็นในนั้นเป็นแค่ base64 ซึ่ง **ไม่ใช่การเข้ารหัส** — ถอดกลับได้ทันที ห้าม screenshot ห้ามแปะใน ticket เด็ดขาด เป็นเรื่อง compliance ไม่ใช่แค่มารยาท

## สรุป: สามประโยคที่พาไปได้ทั้งชีวิตทำงาน

- **pod ไม่ขึ้น → ดู Events · พังหลังรัน → ดู Logs** (ย้ำครั้งท้ายสุด)
- **Running ไม่ได้แปลว่าพร้อมใช้ — ดูตัวเลข READY**
- **ไม่แน่ใจ = ถาม · ถามช้าไป 5 นาที ดีกว่ากดผิดแล้วระบบลูกค้าล่ม**

เชื่อมกลับไปหาฟู้ดทรัคจากตอนที่แล้วก็ได้: Docker ทำให้กล่องขับไปจอดไหนก็ขายได้ ส่วน K8s คือผู้จัดการคลังที่ดูแลให้กล่องทุกใบตื่นมาขายเช้านี้เอง — แม้เมื่อคืนจะมีบางใบตายไปตอนตีสาม

ลองเล่น **เกมล่ารหัสลับ (k8s-clinic-simulator)** ที่แนบมากับคอร์สนี้ดู — เปิดใน browser ได้เลยไม่ต้องต่อ cluster จริง ข้างในมีร้านกาแฟที่พังอยู่ 5 จุด รอเพียงคนที่จำ 4 คำนี้ไปตอบ: **EVENTS · PREVIOUS · READY · LOGS**
