# เริ่มต้นใช้งาน ArgoCD

![Image 2](https://miro.medium.com/v2/resize:fit:700/1*mBt68U7ve74FqRqcaftHrQ.jpeg)

สมมติเราเก็บ Kubernetes manifest ไว้ใน Git แล้วมีคนเข้า Cluster ไปแก้ Deployment ด้วยมือ ตอนนี้ Git บอกอย่างหนึ่ง แต่ Cluster ทำอีกอย่าง เหมือนพิมพ์แบบบ้านไว้ว่า “ประตูสีขาว” แต่ช่างหน้างานทาสีแดง แล้วไม่มีใครรู้ว่าเอกสารหรือของจริงคือคำตอบสุดท้าย

Argo CD ช่วยแก้ปัญหานี้ด้วยแนวคิด GitOps: Git เป็นแหล่งความจริงของ Desired state ส่วน Argo CD คอยเปรียบเทียบกับ Live state ใน Kubernetes แล้วแสดง Drift หรือ Sync ให้กลับมาตรงกัน

บทความนี้จะติดตั้ง Argo CD ทดลอง เข้า UI สร้าง Application และวางแนวทางเปิดใช้งานอย่างปลอดภัยในปี 2026 ครับ

## สิ่งที่ต้องมี

- Kubernetes cluster สำหรับทดลอง
- `kubectl` ที่เชื่อม Cluster ได้
- Git repository ที่มี Kubernetes manifest, Helm chart หรือ Kustomize
- สิทธิ์ติดตั้ง CRD และ Resource ของ Argo CD
- Argo CD CLI ถ้าต้องการสั่งงานผ่าน Terminal

ก่อนทำอะไร ตรวจ Context ให้ชัด:

```bash
kubectl config current-context
kubectl cluster-info
```

ถ้าไม่ใช่ Cluster ที่ต้องการ:

```bash
kubectl config get-contexts
kubectl config use-context <context-name>
```

นี่เป็นขั้นตอนสั้นที่สุดแต่สำคัญที่สุด เพราะ `kubectl apply` ไม่มีปุ่มย้อนเวลาให้เราหลังเผลอติดตั้งของทดลองลง Production ครับ

## ติดตั้ง Argo CD จาก Manifest ทางการ

สร้าง Namespace:

```bash
kubectl create namespace argocd
```

ติดตั้ง Manifest จาก Stable branch ตามเอกสารทางการ:

```bash
kubectl apply \
  --namespace argocd \
  --server-side \
  --force-conflicts \
  -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
```

สำหรับ Lab คำสั่งนี้สะดวก แต่ Production ควร Pin Version ที่ผ่านการทดสอบแทนการดึง `stable` ซึ่งเปลี่ยนตามเวลา และควรเก็บการตั้งค่าติดตั้งไว้ใน Git เพื่อ Review และทำซ้ำได้

รอ Pod พร้อม:

```bash
kubectl wait \
  --for=condition=Ready pod \
  --all \
  --namespace argocd \
  --timeout=300s
```

ตรวจสถานะ:

```bash
kubectl get pods,svc -n argocd
```

ถ้ามี Pod ไม่ขึ้น อย่ารีบลบแล้วลงใหม่ เปิด Event และ Log ก่อน:

```bash
kubectl describe pod <pod-name> -n argocd
kubectl logs <pod-name> -n argocd
```

## เข้า UI แบบปลอดภัยสำหรับการทดลอง

วิธีง่ายที่สุดคือ Port forward Service มาที่เครื่องเรา:

```bash
kubectl port-forward svc/argocd-server -n argocd 8080:443
```

เปิด `https://localhost:8080` Browser อาจเตือน Certificate เพราะเป็น Certificate ภายในของ Lab

Username เริ่มต้นคือ `admin` ส่วน Password ดึงด้วย CLI:

```bash
argocd admin initial-password -n argocd
```

หรืออ่าน Secret โดยตรง:

```bash
kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath="{.data.password}" | base64 -d
echo
```

Login แล้วควรเปลี่ยน Password ปิดบัญชี Admin เริ่มต้นเมื่อมี SSO/RBAC พร้อม และลบ Initial secret ตามคำแนะนำของระบบ รหัสเริ่มต้นเหมือนกุญแจสำรองที่วางใต้พรม ใช้เข้าบ้านครั้งแรกได้ แต่ไม่ควรปล่อยไว้ตรงนั้นตลอดครับ

## สร้าง Application แรก

Application บอก Argo CD สามเรื่องหลัก:

1. Source อยู่ Git repository ไหน Path หรือ Chart อะไร
2. Destination เป็น Cluster และ Namespace ใด
3. Sync policy เป็น Manual หรือ Automatic

ตัวอย่าง Manifest:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: guestbook
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/argoproj/argocd-example-apps.git
    targetRevision: HEAD
    path: guestbook
  destination:
    server: https://kubernetes.default.svc
    namespace: guestbook
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

Apply:

```bash
kubectl apply -f guestbook-application.yaml
```

ตรวจผ่าน CLI:

```bash
argocd app get guestbook
argocd app sync guestbook
```

`prune: true` อนุญาตให้ลบ Resource ที่ถูกนำออกจาก Git และ `selfHeal: true` แก้ Drift ใน Cluster ให้กลับตาม Git ทั้งคู่ทรงพลังมาก ควรเปิดหลังเข้าใจผลลัพธ์และมี Policy ป้องกัน Resource สำคัญ ไม่ใช่เปิดทุกอย่างแล้วหวังว่า Argo CD จะอ่านใจทีมออกครับ

## Sync status กับ Health status คนละเรื่อง

- **Synced** หมายถึง Live manifest ตรงกับ Desired state ใน Git
- **Healthy** หมายถึง Resource ทำงานตามเกณฑ์สุขภาพของ Argo CD

แอปอาจ Synced แต่ Degraded ได้ เช่น Deployment ใน Git สั่ง 3 Replica และ Cluster มี Manifest ตรงกัน แต่ Pod CrashLoop ทั้งหมด ในทางกลับกันแอปอาจ OutOfSync แต่ผู้ใช้ยังใช้งานได้

ดังนั้นตอนแก้ปัญหาอย่ามองไฟเขียวดวงเดียว ให้ดูทั้ง Sync, Health, Event และ Log ของ Workload ครับ

## เปิดผ่าน Ingress โดยรักษา TLS ให้ครบเส้นทาง

บทความเดิมเลือกตั้ง `server.insecure: "true"` เพื่อให้ TLS จบที่ Ingress วิธีนี้ใช้ได้เมื่อออกแบบ TLS termination ไว้ชัด แต่ชื่อ `insecure` ชวนให้เปิดตามกันโดยไม่เข้าใจ

ใน Production มีสองแนวหลัก:

- **TLS passthrough** ให้ Argo CD Server จัดการ TLS
- **TLS termination ที่ Ingress** แล้วส่ง HTTP ภายใน Network ที่ควบคุม โดยตั้งค่า Server ให้สอดคล้อง

ถ้าใช้ NGINX Ingress และ TLS termination ตัวอย่างพื้นฐาน:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: argocd-server
  namespace: argocd
  annotations:
    nginx.ingress.kubernetes.io/backend-protocol: "HTTPS"
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - argo.example.com
      secretName: argocd-tls
  rules:
    - host: argo.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: argocd-server
                port:
                  number: 443
```

Config จริงขึ้นกับ Ingress controller, Certificate manager และรูปแบบ gRPC/HTTP ของ Argo CD ให้อ้างอิงเอกสารของ Controller ที่ใช้ อย่า Copy Annotation จาก NGINX ไปใส่ Traefik หรือ ALB แล้วคาดหวังว่าจะพูดภาษาเดียวกันครับ

## ถ้าจำเป็นต้องตั้ง server.insecure

ใช้ ConfigMap ที่ Argo CD รู้จัก:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cmd-params-cm
  namespace: argocd
  labels:
    app.kubernetes.io/name: argocd-cmd-params-cm
    app.kubernetes.io/part-of: argocd
data:
  server.insecure: "true"
```

```bash
kubectl apply -f argo-config.yaml
kubectl rollout restart deployment argocd-server -n argocd
```

เปิดเฉพาะเมื่อ TLS จบที่ Proxy/Ingress และ Traffic ภายในถูกควบคุม อย่าเปิด HTTP ออก Internet ตรง ๆ ข้อมูล Argo CD มีทั้งสถานะระบบ Repository และความสามารถ Deploy จึงไม่ใช่หน้า Admin ที่ควรตั้งแบบ “เดี๋ยวค่อยล็อกทีหลัง” ครับ

## จัดการสิทธิ์และ Secret

ก่อนใช้งานจริงควรทำอย่างน้อย:

- เชื่อม SSO/OIDC และกำหนด RBAC ตามทีม
- จำกัด Project ว่า Deploy Repository และ Cluster ใดได้
- ใช้ Credential ที่อ่าน Repository เท่าที่จำเป็น
- แยก Namespace และ ServiceAccount ตามขอบเขต
- ไม่เก็บ Secret plaintext ใน Git
- ใช้ External Secrets, Sealed Secrets หรือระบบ Secret management ที่ทีมรองรับ
- เปิด Audit log และติดตามการ Sync ที่ผิดปกติ

GitOps ไม่ได้แปลว่าเอาทุกอย่างใส่ Git แบบอ่านได้ Secret ยังต้องเข้ารหัสหรืออ้างอิงจากแหล่งที่ปลอดภัยครับ

## ภาพรวมหลัง Login

เมื่อเข้า UI เราจะเห็น Application, Sync status และ Health ของ Resource เป็นแผนผัง ช่วยให้ตามเส้นทางจาก Application ลงไป Deployment, ReplicaSet และ Pod ได้ง่าย

![Image 3](https://miro.medium.com/v2/resize:fit:700/1*-V2JyXUv-dKx_LcTSLmGGg.png)

หน้าจอนี้มีประโยชน์มากเวลา Debug แต่ Git ยังควรเป็นจุดที่เราแก้ Desired state การแก้ Live resource ด้วยมือแล้วปล่อยให้ Argo CD เขียนทับกลับมา เป็นการเล่นชักเย่อกับหุ่นยนต์ที่ไม่เหนื่อยครับ

## Checklist ก่อนใช้จริง

- Pin เวอร์ชัน Argo CD และวางแผนอัปเกรด
- สำรองและทดสอบการกู้คืน Config สำคัญ
- เปิด TLS และจำกัด Network access
- เปลี่ยน Initial password และตั้ง SSO/RBAC
- แยก Argo CD Project ตามขอบเขตทีม
- Review `prune` และ `selfHeal` ก่อนเปิด Automatic sync
- กำหนด Resource exclusions หรือ Sync wave เมื่อจำเป็น
- เก็บ Manifest ของ Argo CD และ Application ใน Git
- ติดตาม Metrics, Audit log และ Notification

## สรุป

Argo CD เปลี่ยนการ Deploy จาก “ใครจำคำสั่งได้ก็เข้า Cluster ไป Apply” เป็น Workflow ที่ Git บอกว่าระบบควรหน้าตาอย่างไร แล้ว Controller คอยตรวจของจริงให้ตรงตามนั้น

เริ่มจาก Port forward ใน Lab สร้าง Application หนึ่งตัว และเรียนรู้ความต่างระหว่าง Synced กับ Healthy ก่อน จากนั้นค่อยเพิ่ม Ingress, TLS, SSO, RBAC และ Automatic sync ทีละชั้น GitOps ที่ดีไม่ใช่แค่ Deploy อัตโนมัติเร็วขึ้น แต่ทำให้ทีมตอบได้ด้วยว่าใครเปลี่ยนอะไร เปลี่ยนเมื่อไร และ Cluster ควรกลับไปอยู่สถานะไหนครับ
