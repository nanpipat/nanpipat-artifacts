# 5 เคล็ดลับ การใช้ Chrome Dev Tools ที่ Web Developer ไม่ควรพลาด

Chrome DevTools เปรียบเหมือนห้องควบคุมหลังเวทีของเว็บไซต์ครับ หน้าเว็บที่ผู้ใช้เห็นคือเวทีสวย ๆ ส่วน DevTools คือบริเวณที่เรามองเห็นสายไฟ ฉาก กลไก และคนที่กำลังวิ่งแก้ปัญหากันอยู่ข้างหลัง

หลายคนเปิด DevTools เพื่อดู `console.log()` หรือจิ้ม CSS แล้วปิด แต่จริง ๆ มันทำได้มากกว่านั้นเยอะ ทั้งวัดความเร็ว ถ่ายภาพหน้าเว็บ จำลองตำแหน่ง และทดลองแก้เนื้อหาโดยไม่แตะ Source Code บทความนี้จะพาไปรู้จัก 5 ลูกเล่นที่หยิบใช้ได้จริง และยังใช้ได้ดีในปี 2026 ครับ

> ภาพประกอบมาจาก Chrome เวอร์ชันเดิม หน้าตาเมนูในเวอร์ชันใหม่อาจขยับไปบ้าง แต่ชื่อเครื่องมือและแนวคิดยังเหมือนเดิม ถ้าหาเมนูไม่เจอ ให้กด Command Menu แล้วค้นชื่อคำสั่งได้เลย

## 1. ดูลำดับการโหลดหน้าเว็บแบบเฟรมต่อเฟรม

เวลาเว็บช้า เรามักได้ยินประโยคคลาสสิกว่า “เครื่องผมเร็วอยู่นะ” แต่ความรู้สึกไม่ใช่หน่วยวัดครับ แท็บ Network ช่วยให้เราเห็นว่า Browser ขอไฟล์อะไรบ้าง แต่ละไฟล์เริ่มตอนไหน ใช้เวลานานแค่ไหน และจังหวะใดที่หน้าจอเริ่มแสดงผลจริง

เริ่มจากขั้นตอนนี้:

1. เปิด DevTools แล้วเลือกแท็บ **Network**
2. เปิด Settings ของ Network และเลือก **Capture screenshots**
3. เปิด **Disable cache** เมื่อต้องการวัดการเข้าเว็บครั้งแรก โดยตัวเลือกนี้ทำงานขณะที่ DevTools เปิดอยู่
4. กด `Ctrl + R`, `Cmd + R` หรือปุ่ม Reload

![Image 2](https://miro.medium.com/v2/resize:fit:1000/1*CGDrxHkHpj9buV_Zb4MH4Q.png)

แถบภาพด้านบนจะทำหน้าที่เหมือนกล้องวงจรปิดของหน้าเว็บ เราเลื่อนดูได้ว่าช่วง 500 มิลลิวินาทีแรกผู้ใช้เห็นอะไร ช่วงไหนจอยังขาว และ Element สำคัญโผล่มาตอนไหน

![Image 3](https://miro.medium.com/v2/resize:fit:1000/1*XEJPZVwBJIiTSGtZuWVREg.png)

อย่าดูแค่คำว่า `Finish` เพราะเว็บอาจโหลดไฟล์เบื้องหลังต่ออีกนาน ให้สนใจสิ่งที่ผู้ใช้รู้สึกด้วย เช่น เนื้อหาหลักปรากฏเร็วไหม รูปใหญ่ดัน Layout หรือเปล่า และปุ่มกดตอบสนองทันหรือยัง ถ้าจะตรวจจริงจังต่อ ให้เปิดแท็บ Performance หรือ Lighthouse เพื่อดู Core Web Vitals และต้นเหตุที่ Main Thread ติดงานครับ

เคล็ดลับเล็ก ๆ คือคลิกขวาที่แถวหัวตาราง Network แล้วเปิดคอลัมน์อย่าง **Priority**, **Initiator** และ **Protocol** เราจะเห็นทั้งลำดับความสำคัญ ใครเป็นคนเรียกไฟล์นั้น และการเชื่อมต่อใช้ HTTP/2 หรือ HTTP/3 หรือไม่ ภาพของปัญหาจะชัดขึ้นกว่าการจ้องตัวเลขเวลาเพียงคอลัมน์เดียว

## 2. ถ่าย Screenshot ได้ทั้งหน้าโดยไม่ต่อภาพเอง

เคยเจอหน้า Landing Page ยาวจน Screenshot หนึ่งหน้าจอเก็บไม่หมดไหมครับ วิธีเดิมคือลาก Capture หลายรอบแล้วเอาไปต่อเหมือนต่อแผนที่โจรสลัด แต่ DevTools ทำให้จบได้ในไม่กี่วินาที

1. เปิด DevTools
2. กด `Ctrl + Shift + P` บน Windows/Linux หรือ `Cmd + Shift + P` บน macOS
3. พิมพ์คำว่า `screenshot`

![Image 4](https://miro.medium.com/v2/resize:fit:700/1*EoswevMZxqTsnVcng3xbSA.png)

Command Menu จะแสดงคำสั่งหลายแบบให้เลือก

![Image 5](https://miro.medium.com/v2/resize:fit:541/1*jtV41ym2vvrYSTI_cnp3Tw.png)

- **Capture area screenshot** ลากเลือกเฉพาะบริเวณที่ต้องการ
- **Capture full size screenshot** ถ่ายทั้งหน้า แม้เนื้อหาจะยาวเกินหน้าจอ
- **Capture node screenshot** ถ่ายเฉพาะ Element ที่เลือกในแท็บ Elements
- **Capture screenshot** ถ่ายเฉพาะ Viewport ปัจจุบัน

กรณี Capture node มีประโยชน์มากเวลาส่งบั๊กให้ทีม เช่น ต้องการภาพเฉพาะ Card ที่ข้อความล้น เราเลือก Node แล้ว Capture ได้พอดี ไม่ต้อง Crop จนขอบหาย

ถ้าหน้าเว็บมี Lazy Load ให้เลื่อนผ่านเนื้อหาก่อนหนึ่งรอบเพื่อให้รูปโหลดครบ และตรวจ Sticky Header ด้วย เพราะบางเว็บอาจทำให้ Header โผล่ซ้ำในภาพยาว นี่ไม่ใช่ DevTools งอแง แต่เป็นผลจากวิธีที่หน้าเว็บจัดตำแหน่ง Element ครับ

## 3. เปิด Design Mode แล้วแก้ข้อความเหมือนเอกสาร

บางครั้งเรายังไม่อยากแก้โค้ด แค่อยากตอบคำถามว่า “ถ้าหัวข้อนี้ยาวขึ้นอีกสองเท่า Layout จะรอดไหม” เปิด Console แล้วใช้คำสั่งนี้ได้เลย:

```javascript
document.designMode = "on";
```

![Image 6](https://miro.medium.com/v2/resize:fit:318/1*3TE2HOeYe3ETPhuDqFcdgg.png)

หลังจากนั้นข้อความบนหน้าจะถูกแก้ได้คล้ายเอกสาร เราสามารถลองพิมพ์ชื่อสินค้ายาว ๆ ใส่ภาษาไทยกับ Emoji หรือลบเนื้อหาบางส่วนเพื่อดูว่า Layout รับมืออย่างไร

![Image 7](https://miro.medium.com/v2/resize:fit:700/1*b0a0NfmMQwJYTMqP9kdB8Q.png)

เมื่อทดลองเสร็จ ให้ปิดด้วย:

```javascript
document.designMode = "off";
```

สิ่งที่แก้มีผลเฉพาะหน้าเว็บใน Browser ของเราและหายเมื่อ Reload จึงเหมือนใช้ปากกาไวต์บอร์ดวาดทับแบบชั่วคราว ไม่ได้เปลี่ยนข้อมูลจริงบน Server

ถ้าต้องปรับ HTML หรือ CSS อย่างละเอียด ให้แก้ผ่านแท็บ Elements แทน และถ้าต้องการเก็บการแก้ไว้ระหว่าง Reload ลองศึกษา Local Overrides ต่อได้ แต่อย่าลืมว่าเครื่องมือเหล่านี้เหมาะกับการทดลองและ Debug ไม่ใช่วิธีแก้ Production โดยตรงครับ

## 4. จำลองตำแหน่งและ Sensor โดยไม่ต้องเดินทางจริง

ถ้าเว็บมีฟีเจอร์ค้นหาร้านใกล้ตัว เราคงไม่อยากบินไปโตเกียวเพียงเพื่อทดสอบว่าปุ่มใช้ได้ไหม DevTools จำลองพิกัดให้ได้

1. เปิด Command Menu ด้วย `Ctrl/Cmd + Shift + P`
2. ค้นหา `Show Sensors`
3. เลือกตำแหน่งสำเร็จรูป หรือกรอก Latitude, Longitude และ Timezone เอง

![Image 8](https://miro.medium.com/v2/resize:fit:700/1*5VFyaOHJ9Z9626INPy0rIw.png)

แผง Sensors จะปรากฏด้านล่าง

![Image 9](https://miro.medium.com/v2/resize:fit:700/1*MfQLWAVWDBXB_6Vr9yTu8w.png)

จากนั้น Reload หน้าและอนุญาต Location ให้เว็บไซต์ เราสามารถทดสอบกรณีสำคัญได้ เช่น:

- อยู่ในพื้นที่ที่บริการรองรับ
- อยู่นอกเขตบริการ
- ไม่อนุญาต Location
- ไม่มีข้อมูลตำแหน่ง
- Timezone ต่างจากเครื่องของเรา

ต้องจำไว้ว่า Geolocation บนเว็บมักต้องทำงานผ่าน HTTPS และผู้ใช้ต้องให้สิทธิ์ การจำลองพิกัดไม่ได้ข้าม Permission Model ของ Browser นอกจากนี้ Sensors บางเวอร์ชันยังจำลอง Orientation และ Idle state ได้ เหมาะกับเว็บที่ตอบสนองต่อการหมุนอุปกรณ์หรือสถานะผู้ใช้ครับ

## 5. คัดลอกรูปเป็น Data URL และรู้ว่าเมื่อไรไม่ควรใช้

ใน Network เราสามารถเปิดรูปที่เว็บโหลดมา แล้วคัดลอกเป็น Data URL ได้

1. เปิดแท็บ Network แล้วกรองประเภท `Img`
2. Reload หน้าเว็บถ้ายังไม่มีรายการ
3. เลือกรูปและเปิดแท็บ Preview

![Image 10](https://miro.medium.com/v2/resize:fit:636/1*47S4CWMJjWtXKnvglWoGyw.png)

คลิกขวาที่ภาพแล้วเลือก **Copy image as data URI**

![Image 11](https://miro.medium.com/v2/resize:fit:311/1*KrkXa4P5Xwpxly3ZQ_mjQw.png)

เมื่อ Paste จะได้ข้อความยาวหน้าตาประมาณนี้:

```text
data:image/png;base64,iVBORw0KGgoAAAANSUhEUgAA...
```

![Image 12](https://miro.medium.com/v2/resize:fit:700/1*MCr6nTiXE7ZQZ_Ex5Mcvdg.png)

Data URL เหมือนย้ายรูปทั้งใบเข้าไปอยู่ในข้อความ เหมาะกับภาพเล็กมาก ๆ, Prototype, Email บางกรณี หรือเวลาต้องส่งตัวอย่างที่ไม่อยากพึ่งไฟล์ภายนอก แต่ไม่ควรเอารูปใหญ่ทุกภาพมาแปลง เพราะ Base64 ทำให้ข้อมูลโตขึ้นและ Browser Cache แยกรูปนั้นได้ยากกว่าไฟล์ปกติ

อีกเรื่องคือสิทธิ์ใช้งานภาพ การคัดลอกได้ไม่ได้แปลว่าได้รับอนุญาตให้นำไปเผยแพร่ต่อ DevTools เป็นไขควงสำหรับตรวจของ ไม่ใช่ใบอนุญาตหยิบของกลับบ้านครับ

## ก่อนปิด DevTools ลองจำสามคำถามนี้ไว้

ทุกครั้งที่ Debug เว็บ ลองถามตัวเองว่า:

1. สิ่งที่ผู้ใช้เห็นเกิดขึ้นตอนไหน
2. Browser กำลังรอ Resource หรืองาน JavaScript ตัวใด
3. เราจำลองกรณีผิดปกติได้ไหม โดยไม่ต้องแก้ Production

DevTools เก่งที่สุดเมื่อเราใช้มันเป็นเครื่องมือสืบสวน ไม่ใช่เพียงหน้าต่างดู Error ยิ่งฝึกมอง Network, DOM, Performance และ Sensors เป็นเรื่องเดียวกัน เราจะยิ่งแก้บั๊กได้เหมือนนักสืบที่ไม่ได้เห็นแค่รอยเท้า แต่เห็นทั้งเส้นทางที่คนร้ายเดินมาครับ

อ่านต่อจากเอกสารทางการ: [Chrome DevTools](https://developer.chrome.com/docs/devtools/)
